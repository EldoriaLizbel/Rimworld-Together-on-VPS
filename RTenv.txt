RimWorld Together on VPS — Current Environment

Target: Ubuntu Server 22.04 x86-64, Docker Engine and Compose >= 2.24.4.
Host-side operator scripts use Python >= 3.10 (stdlib); FastAPI uses Python 3.12 in Docker.
Fresh VPS Compose project: rimworld-together-vps
Local development Compose project: rimworld-together-on-vps-nonprod
Pinned game binary: upstream 26.8.31.1, Linux amd64, native listener TCP 25555.

Services and access
- web (Next.js/Node): loopback by default, host TCP 10005 -> container 3000.
  Browser talks only to web. The server authenticates against PostgreSQL and
  forwards allowlisted game actions to api:8000 using a private token.
- api (FastAPI): port 8000 on app_network only. The API independently checks
  each user's database role. Worker tasks run here, without another container.
- postgres: port 5432 on app_network only. Named postgres_data volume. The web
  and game API have separate SQL roles; neither is the PostgreSQL owner.
- rimworld: independent game process supervised by Python; game binds inside
  the container, with host TCP 25555 configurable. Public VPS default 0.0.0.0,
  local development default 127.0.0.1. The API mounts game files read-only.
- A single app_network carries service traffic. No container has a Docker
  socket mount. No proxy, extra worker container, or public DB/API is required.

First install: sh deploy.sh; public IPv4 detection is best effort.
Use RIMWORLD_PUBLIC_HOST=<your-IP-or-DNS> sh deploy.sh for a floating IP or NAT.
See README.md and docs/operations.md for scoped deploy, backup, restore, rollback,
port/firewall setup and external smoke tests.

Persistence and startup
- .rwt-deploy/game (VPS), data/nonprod/rimworld (local) holds native worlds,
  saves, supported settings and accounts. First player to complete world
  generation determines the shared seed in Assets/WorldValuesFile.json.
- game_bridge (named volume) carries the allowlisted operation request,
  stage, boot ID, heartbeat, interpreted event inputs and log spool.
  The supervisor processes only known operations; it never controls Docker.
- PostgreSQL starts and must pass an authenticated SELECT before migrations.
  The checksummed schema_migrations ledger records verified legacy baselines
  or migrations applied under transactions and a PostgreSQL advisory lock.
- API waits on PostgreSQL; web health checks DB and API contract. Game
  readiness uses recent supervisor heartbeat, TCP, and a consistent current
  world/config snapshot. The game can listen without the dashboard.
- Release state and append-only operation outcomes are private under
  .rwt-deploy. Scoped updates leave unrelated services and data intact.

PostgreSQL tables
- user_profile: Dashboard accounts (bcrypt); roles user/superuser.
- dashboard_sessions / dashboard_login_budget: revocable session token
  digests and persistent sign-in attempt limits.
- world_config: native config snapshot, revision, initialized flag, boot ID.
- server_log: parsed event and raw diagnostic log data, rolling 7 days;
  a game config apply or factory reset starts a new log timeline.
- player_data: account/settlement metadata, observed login/save, colony
  name and size when the native save format supplies them.
- player_online_sample / worker_sample: one-minute observations for 7 days.
- schema_migrations: version, source checksum, timestamp, baseline, duration.

Dashboard
- Overview: read-only status, published address, shared seed, settings and
  player activity as permitted by role. Worker: health, used/available RAM,
  online player count, uptime and log, refreshing about once per minute.
- Config server: editable native values grouped with descriptions and units.
  Save stages changes; confirm Restart to apply. Allowed settings include
  name/limits, chat/backup behavior, native action toggles/cooldowns,
  compatible difficulty and enforcement, and existing event prices.
  Native bind settings, world/seed, rules without native support, mod
  membership/load order and event definition IDs are not editable here.
  Road/site/event prices use Silver; cooldowns use milliseconds; backup
  schedule uses hours.
- Factory reset restores dashboard-editable native fields and game password
  to defaults from the pinned binary and restarts only the game. Default
  server-listing/telemetry settings come from upstream. World, saves, mod
  membership and accounts remain intact.
- Player accounts: dashboard users and game users are distinct. A confirmed
  native resetplayer clears that player's active game data after the game's
  backup. It keeps the game login and dashboard account. No mass reset is
  part of any deployment.
- Admin writes require an authenticated superuser and an allowed origin;
  restart, factory reset and player reset also require explicit confirmation.

Configuration inventory
- Deploy/private compose.env: COMPOSE_PROJECT_NAME; RWT_WEB_ENV_FILE,
  RWT_POSTGRES_ENV_FILE, RWT_GAME_DATA (managed paths); RIMWORLD_API_DB_NAME,
  RIMWORLD_API_DB_PASSWORD (secret), RIMWORLD_API_TOKEN (secret).
- Network: RIMWORLD_HOST_PORT/BIND, RIMWORLD_PUBLIC_HOST, RIMWORLD_WEB_PORT/BIND,
  Optional public dashboard binding requires deliberate configuration.
- Runtime options: TZ; POSTGRES_VERSION (pinned on first VPS installation);
  RWT_WEB_MEMORY, RWT_API_MEMORY, RWT_POSTGRES_MEMORY, RWT_GAME_MEMORY,
  RWT_GAME_CPUS (0/unset = no extra Compose limit).
- Backup options: RWT_BACKUP_DIR, RWT_BACKUP_MAX_COUNT, RWT_BACKUP_MAX_DAYS,
  RWT_BACKUP_MIN_KEEP.
- postgres.env: POSTGRES_USER, POSTGRES_DB, POSTGRES_PASSWORD (secret),
  RIMWORLD_WEB_DB_PASSWORD (secret), RIMWORLD_ADMIN_PASSWORD (initial seed
  only; changing this env alone will not change an existing admin password).
- web.env: DATABASE_URL (secret), SESSION_SECRET (secret), COOKIE_SECURE
  (true only behind HTTPS), optional DASHBOARD_ORIGIN (exact browser origin,
  including scheme/port).
- Direct compose.prod.yaml use: RWT_WEB_IMAGE, RWT_API_IMAGE,
  RWT_RIMWORLD_IMAGE; set immutable references.
  Managed release deployments use a validated per-service overlay for mixed
  versions. Use project scripts to preserve release state and rollback.

Limitations
- Public HTTP is not encrypted. Optional dashboard bind is a deliberate
  operator choice. Default to an SSH tunnel or an HTTPS reverse proxy.
- Local backups help recovery from bad deployments/configuration; copy
  them off host for VPS and disk loss. Treat backup files as secrets.
- TCP readiness does not verify actual RimWorld client login or save
  compatibility. Keep the upstream game version pinned until a separate
  maintenance and compatibility test with real clients/saves.
